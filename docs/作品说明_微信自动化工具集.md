# 微信自动化工具集 · 作品说明

> 版本：2026-09-12 · 作者：本机 AI 协作会话产出
> 位置：`__ROOT__\`
> 定位：在已跑通的微信服务之上，封装一层**带安全护栏的调用与验证工具**。

---

## 一、这个作品是什么

一句话：**在本机微信 4.1.13.12 上，把「读历史 / 发消息 / 验证落库」做成可复用、带前置校验的命令行工具。**

它不是从零造轮子。底层三条链路已经由 `wechat-service` 项目跑起来了，我这一层只做四件事：

| 我做的 | 不做的 |
|---|---|
| 调用网关 API | 不改微信、不写 hook |
| 前置校验（防误发） | 不动项目源码 |
| 发送后回读验证 | 不改 `trigger_safe.py` |
| 封装成可复用脚本 | 不做无人审阅的代发 |

## 四、三个核心工程决策

### 决策 1：发送前必须校验「当前打开的会话 == 目标」

微信的发送作用于**当前打开的会话**，不是指定会话。
早期脚本没校验，把测试消息发进了真实群（项目文档记录的真实事故）。

所以每一次发送前都执行：

```python
current = rpc("get_current_chat")
if current not in {target_name, target_wxid}:
    abort()          # 不切会话、不发送
```

循环脚本里**每一轮都重查**，不是只在开头查一次。

### 决策 2：发送回执不可观测 → 数据库回读是唯一真凭据

`wechat.message.send_text` 在能力表里是 `verified: false` / `SEND_RESULT_NOT_OBSERVABLE`。

实测发现更关键的一点：

```
[T+0s]  网关返回 SENT_VERIFIED（UIA 侧观测到）
[T+3s]  读数据库 → 0 条新消息   ← 差点误判失败
[T+12s] 读数据库 → message_id 368 出现
```

**UIA 动作与 WAL 落库之间存在 3–12 秒时差。**
所以验证逻辑必须是**轮询**，且以数据库行为为准，不信返回值。

### 决策 3：目标解析要四重对齐

```
昵称  →  wxid  →  微信号  →  备注
```

实测案例：会话显示名「好友A」，消息发送者名却是「好友D」。
最终用 `contact.db` 一行定案：

```
username(wxid) = wxid_EXAMPLE_FRIEND_A
alias(微信号)   = example_alias_a
remark(备注)    = 好友A
nick_name      = Сосновая трава
```

**三个字段指向同一个人，才认定目标无误。**

## 六、安全边界（设计约束，不是事后补的）

1. **不修改 `wechat-service` 任何源码**，不改 hook、不改 YARA、不改偏移
2. **不动 `hook/trigger_safe.py` 的硬约束** —— 它把「只允许发文件传输助手」写死
3. **前置校验失败即中止**，不做「先切会话再发」的兜底
4. **唯一 request_id** —— 网关按 id 幂等，网络重试不会重复发
5. **停止机制** —— `Ctrl+C` 或创建 `work/STOP_SEND` 文件
6. **不做无人审阅的代发** —— 面向真人的自动回复不在本作品范围内

## 七、已知限制

| 限制 | 说明 |
|---|---|
| 落库时差 | UIA 返回后 3–12 秒数据库才有记录 |
| 发送不可观测 | 返回值不代表已送达，必须回读 |
| 群成员信息 | UIA 无稳定节点，`NOT_SUPPORTED` |
| 朋友圈 | 未实现 |
| CDN-only 图片 | 本地无缓存 |
| UIA 导航 | 历史成功率 0%（实测 `TARGET_OPEN_FAILED`），靠「目标会话已打开」兜底 |
| 通话内容 | 归档只有 `[通话]` 标记，无音频、无时长 |
| 管道单实例 | 调试前必须先停计划任务 `wxwal-hook-daemon` |

## 十、一句话总结

**这套东西的价值不在"能发消息"，在于它知道什么时候不该发。**
每一次发送都经过：目标四重对齐 → 当前会话校验 → 唯一幂等 id → 落库轮询验证。
缺任何一环，都可能在真人身上留下撤不回的痕迹。
